# notediff: Design Document

**Product:** `notediff`, a single-user desktop text editor for plaintext and Markdown with a baseline-comparison “Diff Mode”.

**Platform:** Linux with GTK 4.18, libadwaita 1.7 and GtkSourceView 5.16 or newer. Developed and tested on Debian 13 (trixie), including the ChromeOS Linux environment. Ubuntu 24.04 is too old for the required GTK features.

**Audience:** users and contributors. This document describes the design and the decisions behind it.

**Core philosophy:** The live file is the source of truth. Each document has at most one baseline snapshot, kept in a central folder and advanced hunk by hunk. If the link between a file and its baseline breaks, the user loses only the comparison, never the document.

## 1. Overview

`notediff` behaves as an ordinary text editor until the user enters **Diff Mode**, a split view comparing the live document against a single saved baseline. The live document is on the left and read-only. The baseline is on the right and “catches up” to the live document as the user accepts changes one hunk at a time.

The baseline is a save point, not a history. There is exactly one per file, and accepting a hunk moves it closer to the live text.

## 2. Scope and Constraints

- **Scope:** Localization and multi-user goals remain out of scope for 1.0.
- **Distribution:** source builds and the included `install.sh`/`uninstall.sh` for Linux desktops.
- **Content:** UTF-8 plaintext and Markdown (prose, notes, code). Files that are not valid UTF-8, contain a NUL byte, or exceed 16 MiB are refused at open and reload; a buffer above 16 MiB cannot be saved. Files above 1 MiB trigger a warning at open and reload because diffing runs in-process.
- **Line model:** line breaks follow GtkTextBuffer: `\n`, `\r\n`, a lone `\r`, and U+2029. The core uses the same definition so diff line numbers, indentation and status statistics agree with the editor.
- **Accepted risk:** renaming, moving, or replacing a file outside the app breaks its baseline association. The app does not try to prevent or detect this, but the association can be repaired by hand: **Manage App… → Baseline Snapshots** can link the document to the orphaned baseline (section 5.6). Renaming or moving a file with **Rename or Move** inside the app moves its baseline along, and **Save As** offers to copy the baseline to the new file, so nothing is orphaned. The live file is untouched, and a fresh baseline can be started at any time.
- **Non-goals:** snapshot history, automatic re-linking of snapshots, hunk rejection from inside Diff Mode, collaboration, plugins, and Flatpak packaging.

## 3. Environment and Architecture

### 3.1 Development environment

- **OS:** Linux with GTK 4.18+, libadwaita 1.7+ and GtkSourceView 5.16+. Debian 13 (trixie) is the reference environment; GTK apps also display through the ChromeOS Linux Wayland bridge.
- **Toolchain:** Rust 1.92 or newer via rustup. Debian trixie’s `apt` Rust is 1.85; the GTK bindings and edition-2024 let-chains need a newer toolchain. VS Code with `rust-analyzer` is supported.
- **Libraries:** confirm with `pkg-config --modversion gtk4 libadwaita-1 gtksourceview-5`.
- **System packages needed:** `build-essential`, `pkg-config`, `libgtk-4-dev`, `libadwaita-1-dev`, `libgtksourceview-5-dev`. Install these before opening the project in VS Code, since the GTK crates’ build scripts need them and `rust-analyzer` will otherwise report build-script errors.

### 3.2 Technology choices

| Concern | Choice | Notes |
| --- | --- | --- |
| Language | Rust (2024 edition) | Core invariants are well suited to Rust’s type system and test tooling. The `edition` in `Cargo.toml` is the Rust language edition, not a notediff edition |
| UI toolkit | GTK4 + libadwaita | Via the `gtk4` and `libadwaita` crates |
| Text widget | GtkSourceView 5 | Via the `sourceview5` crate; plain-text editing with undo, search, line numbers, current-line highlighting and bracket matching |
| Diff engine | `similar` crate | Line diffs plus inline (word-level) refinement |

## 4. Storage

### 4.1 Snapshot store location

All baselines live under:

```
$XDG_DATA_HOME/notediff/snapshots/
```

which is normally `~/.local/share/notediff/snapshots/`. No baseline or other persistent artifact is written next to the user’s documents, so project directories stay clean. Live-file saves briefly create a hidden temporary file in the document’s directory for atomic replacement; it is normally removed by the rename or by failure cleanup, though a crash can leave it behind.

### 4.2 Identity and layout

A document’s identity is its **canonical absolute path**, with symlinks resolved. The snapshot mirrors that path under the store:

```
~/.local/share/notediff/snapshots/
  home/you/notes/todo.md                 <- baseline of /home/you/notes/todo.md
  home/you/notes/projects/plan.md        <- baseline of /home/you/notes/projects/plan.md
```

- **Format:** an exact byte-for-byte copy of the baseline text. No metadata file, header or hash. Existence and modification time are sufficient.
- **Size:** baselines use the same 16 MiB cap as documents; the store refuses larger writes.
- **Symlinks:** resolved before mapping, so a symlink and its target share one baseline.
- **Inspectability:** because the layout mirrors the real filesystem, the store can be browsed, diffed with ordinary tools, backed up, or edited by hand.
- **Path conflicts:** if a path later changes from file to directory (or the reverse), a snapshot write may fail. This is treated as a normal write failure (section 7).

### 4.3 Write discipline

- All snapshot writes normally use atomic replace (write a temporary file in the same directory, then rename), so a crash does not leave a half-written baseline. A mount that rejects the rename may use the direct-write fallback described below.
- The temporary file is created with a short name and is never more permissive than the destination while content is written; its exact existing permissions are applied after the write when the filesystem supports chmod. It is removed if the write fails. A failed temp write leaves the existing file untouched.
- Parent directories are created on demand.
- Live-file saves also use atomic replace. Only when the rename itself is rejected by a shared mount does the write fall back to a direct write.
- Snapshots are never modified outside Diff Mode, except by **Create Baseline** (which writes the first baseline for a file), **Rename or Move** (which moves the baseline along with the file), **Save As** (which copies the baseline to the new file on request) and explicit actions in Manage App… → Baseline Snapshots (delete, link, copy). Link and Copy act immediately; deletion requires confirmation. Moving a baseline always writes the destination first and removes the source afterwards, so a failure never loses it.

### 4.4 Chromebook storage notes

- **The snapshot store always lives inside the Linux container**, even when the notes themselves are elsewhere. It is covered by the ChromeOS Linux backup and restore feature, and it is lost if the container is deleted without a backup. If the baselines matter, include the container in backups or periodically copy the snapshot folder elsewhere.
- **Notes can live in either place.** Documents in the container’s home directory are the primary, best-tested case. Documents in ChromeOS folders shared with Linux (under `/mnt/chromeos/`, including Downloads or Drive if shared) also work, because identity is the canonical absolute path in both cases.
- **Caveats for shared ChromeOS folders:** change notification is unreliable (handled by the modification-time check in section 7), the path may be absent when the container starts (also section 7), and file operations may be slower.
- **Atomic replace on shared mounts:** temp-then-rename is attempted first. If the mount rejects the rename after the temporary file has been written, fall back to a direct write for that file and report any failure as a normal write failure. A failure while creating or writing the temporary file never touches the original.
- **One file, two paths:** if the same file is reachable under two different paths, each path gets its own baseline. This falls under the accepted breakage in section 2.

### 4.5 Recent documents

When recent paths exist, the header Open button shows a menu: **Browse…**, then
up to ten recent file paths. Each recent path is a custom two-line row: a bold,
end-ellipsized file name above a smaller, dimmed, middle-ellipsized directory
ending in `/`. Directories below the user's home are shortened to `~/...`;
stored paths and action targets remain absolute. Every row also has a
right-aligned `view-conceal-symbolic` button that removes just that entry
immediately, with no confirmation. The open menu is rebuilt in place and focus
moves to the next row, or the previous row when the last entry was deleted.
When the pruned list is empty, the button opens the chooser directly instead of
showing a one-item menu. **Ctrl+O** and **Open…** always open the chooser
directly, and the header button is unavailable in Diff Mode.

The list lives in `$XDG_DATA_HOME/notediff/recent` as one absolute path per
line, newest first, with no metadata. Canonical paths from successful opens,
Save As and Rename or Move are recorded. Paths that are not valid UTF-8 or
contain control characters are skipped. The list is capped at ten entries;
reopening a path moves it to the front and removes the duplicate.

Nothing is read or stat-ed at startup. The list is loaded when a path is
recorded and when the Open menu is about to be shown. At that point missing
files and duplicates are removed and the file is rewritten only if it changed;
if no entries remain, the state file is deleted. Paths under a shared-volume
mount that is currently unavailable are kept, because they can return when the
volume is reconnected. Removing the final entry deletes the state file. Write
failures are silent because the list is disposable, and deleting an entry never
touches the document itself.

## 5. Key Modules

### 5.1 Standard Editor Mode

- **Find and Replace:** `Ctrl+F` opens the Find bar; `Ctrl+H` or **Replace…** in the main menu reveals a replacement field with **Replace** and **Replace All**. Matching is literal, case-insensitive by default, with a shared **Match Case** toggle. Enter in Find advances to the next match, wrapping at the end. Replace changes only a selection that exactly matches the current search options, then advances; otherwise it only selects the next match. Replace All snapshots non-overlapping matches in the whole buffer and edits them in reverse order, so replacement text is never searched again. Each operation is one undo step. An empty replacement deletes matches, an empty query does nothing, and Replace All reports the match count. Replacement tabs pass through the existing tab-to-space filter. Replace actions are disabled for read-only documents and in Diff Mode; Find is available for read-only documents but disabled in Diff Mode. Entering Diff Mode closes the bar. `window/search.rs` owns this behavior; the GTK smoke test covers matching, wraparound, replacement, undo and guards.
- **Plain-text rendering:** every document is plain text. No language is ever attached to an editor or Diff Mode buffer, and syntax highlighting is disabled explicitly. Markdown headings, emphasis, code spans and list markers therefore appear literally, and `.rs`, `.md` and extensionless files are styled identically. GtkSourceView supplies undo, line numbers, current-line highlighting and bracket matching. Find uses the buffer’s normal selection colours. Theme schemes supply the editor text, selection, cursor, current-line, gutter, bracket and review colours.
- A clean text editor using GtkSourceView, with the usual open, save, search, and undo behavior. **Go to Line** (`Ctrl+G`, also in the menu) opens a small dialog for a line number; out-of-range numbers are clamped to the document. It is disabled while Diff Mode is showing. Clicking or dragging the left line-number gutter selects whole logical lines; the same gesture is installed on both full Diff Mode panes and is disabled in inspection.
- **Word Wrap** is a checked item in the main menu, backed by the boolean window action `win.word-wrap` and the **Alt+Z** accelerator. **Ctrl+W** closes the window; **Ctrl+Q** quits through every window's normal close flow, prompting dirty windows one at a time before the remaining windows close. Each window starts with `WordChar` wrapping. Turning it off sets `None`, so long lines can be scrolled horizontally. This affects the editor display, including read-only files. The setting lasts for the life of that window and the action is disabled while Diff Mode is showing.
- **EOL Conversion** (status-bar line-ending popover with **Windows (CRLF)** and **Unix (LF)**; not in the main menu) rewrites every GTK line break in the buffer to the chosen style: `\n`, `\r\n`, a lone `\r`, and U+2029. The trailing-newline state is preserved. The conversion is one undo step, keeps the cursor's line and column, and leaves the document dirty (the file on disk is untouched until saved, so Create Baseline and Confirm ask to save first). If the text already has that style (or has no line breaks) a toast says so and nothing changes. The action does nothing while Diff Mode is showing and is refused, with a toast, for read-only documents. The logic is `core::eol::convert_line_endings`; the window applies the result.
- **Open File** (`Ctrl+O`, the header-bar button and **Open…** in the File menu). `Ctrl+O` and **Open…** show the chooser directly. When recent paths exist, the header-bar button opens a menu whose first item is **Browse…**, followed by up to ten recent file paths (two-line rows with a bold file name over a smaller, dimmed home-shortened directory ending in `/`, newest first). Each row has a right-aligned `view-conceal-symbolic` button that removes that entry immediately without confirmation; choosing the rest of the row enters the normal Open File flow. When the pruned list is empty, the button opens the chooser directly. The recent list is pruned lazily when the menu is shown, never at startup (section 4.5). After a path is selected, a clean document opens it immediately. A dirty document shows the `Save changes?` prompt, whose body reads `The document has unsaved changes.`, with **Open New Window** (neutral), **Discard Changes** (destructive) and **Save** (suggested); there is no Cancel response button, but Esc and dismissal still abort the pending open. **Open New Window** leaves the current draft untouched. Open File is disabled while Diff Mode is showing, including the header menu button and `win.open-recent`. The selected path is carried through a save by `PendingAction::OpenPath(PathBuf)`. Successful opens, Save As and Rename or Move record the document's canonical path. A canonical path is open in at most one window: `window_for_open_path` scans the window registry before the save prompt and before a new window is created. A different owner is raised with the toast `File is already open in this window`, and the requesting window also shows `File is already open in another window`. A same-window owner is routed to `request_reload`: a dirty document first shows `Reload from Disk?` with the body `The document has unsaved changes.`; a clean document reloads when the disk text differs, and identical text only adopts the new disk mtime while keeping the cursor, scroll and undo history, with the toast `Document is identical with its file on disk`. The lookup also sees a path reserved by a pending Convert Tabs prompt. The header Open button's shortcut tooltip is hidden while its recent menu is visible.
- **New File** (`Ctrl+N`, a header-bar icon beside Open, and a File menu item) replaces the document in the current window with an empty, untitled one. A capture-phase click gesture records whether Shift is held; a Shift-click on the header button opens a new window instead. The shortcut is hidden from the tooltip and menus. A dirty document first gets the same `Save changes?` prompt (`PendingAction::NewFile`), whose neutral **Open New Window** opens an empty window and leaves this draft alone; Esc and dismissal abort the pending new file. `load_document` then resets the buffer, flags, Diff Mode and search bar. The old file and its baseline stay on disk. New File is disabled while Diff Mode is showing, so the Shift shortcut is unavailable there. **New Window** (`Ctrl+Shift+N` and a File menu item) opens an empty window via `open_empty_window`, reusing the caller's snapshot store; the current window and document are untouched, so no save prompt is involved. New Window remains available in Diff Mode.
- **Copy Selected Text.** A flat `edit-copy-symbolic` button immediately right of Open File has tooltip `Copy Selected Text (Ctrl+C)`. Mouse clicks do not steal text focus. Weak focus-controller captures remember the last-focused editor/review view, including keyboard activation after tabbing to the button. In Diff Mode only the active full/inspection pair is eligible; stale hidden selections are ignored. The editor is used in editing mode. The button copies the selected text through the clipboard API, omitting display-only diff markers. Success says `Copied 3 characters to clipboard`, or `Copied 45 characters (6 lines) to clipboard` when more than one line is touched. Unicode scalar characters, including selected line terminators, are counted rather than bytes; trailing LF does not add another touched line. Counts use singular/plural and thousands separators (`core::textstats::copied_text_summary`). With no selection, a warning toast says `No selected text to copy!` and the clipboard is untouched. Read-only views work normally. Inline review highlighting is not a text selection. Copying changes neither the document nor its dirty state or edit clock. In the editor native Ctrl+C is unchanged and shows no toast; Diff Mode panes intercept the copy signal only to omit display-only markers.
- **Save As** (`Ctrl+Shift+S`) saves the draft under a new path, which becomes the document's path. It is unavailable while Diff Mode is showing, like Rename or Move; finish or close the review first. The original file and its baseline are untouched. If the old path has a baseline and the new path has none, a prompt then asks **Copy Baseline** or **No Baseline** (dismissing means no baseline), so Review Changes can compare the new file against the same save point. Copying leaves the original baseline in place and never replaces an existing one (`SnapshotStore::link` with `LinkMode::Copy`). A pending save-then-continue action runs after the prompt.
- **Rename or Move** (`F2`, also in the File menu) opens a small dialog with the current file name. The input is either a new name (rename in place) or a path (move): absolute, relative to the file's folder, or starting with `~/`. A path naming an existing folder, or ending in `/`, moves the file into that folder under its current name. The destination folder must already exist. The baseline moves with the file, so Review Changes keeps working. The input is trimmed; empty input, an invalid name, or a missing destination folder is refused with a toast, a destination equal to the current path does nothing, and a destination already used by another file is refused with an error. A move across filesystems falls back to copy-then-remove, and the last-known mtime is then refreshed so no false external-change prompt follows. A baseline already stored under the new name belongs to a file that does not exist (otherwise the rename would be refused), so it is an orphan and is replaced. The document's text, dirty state and undo history are untouched, because only the path changes, and the last-known mtime is kept so a pending external change is still noticed. If the file is renamed but its baseline cannot be moved, an error says so and the old baseline stays behind as an orphan that Manage App… → Baseline Snapshots can link. The action is disabled while Diff Mode is showing, and an untitled document opens Save As instead. Renaming and moving work on the canonical path, so a symlinked document moves its target. The logic is `core::rename::plan` and `core::rename::rename_document`; the window owns the dialog and refreshes the title and header button afterwards.
- **Browse in Rename or Move.** The dialog's text is “Enter a new name and/or path.”, and the **...** browse button sits to the right of the input. Neither the button nor the input has a tooltip. The button opens a Save-style file chooser starting in the file's folder with its current name. The chosen absolute path is written into the input, and nothing is renamed until the user confirms the dialog, so all the rules above still apply. Choosing a name that is already used is refused at that point, as for typed input.
- **Insert Path** (right-click context menu) is a submenu with **File…** (`win.insert-path`) and **Directory…** (`win.insert-folder-path`). Each opens a chooser starting in the document's folder; File uses the normal open dialog and Directory uses `GtkFileDialog::select_folder`. Both insert the chosen absolute path at the cursor. They behave like a paste: a selection is replaced, the inserted path stays selected, the edit is one undo step, and the document becomes dirty. Nothing is read, so there is no size, UTF-8, contents or folder-permission check and no large-file prompt. Both actions are disabled for read-only documents and do nothing in Diff Mode. The insert logic lives in `window/editing.rs`.
- **Add Text from File…** (right-click context menu, `win.insert-file`) lets the user choose a file and inserts its entire contents at the cursor, like a paste: a non-empty selection is replaced, the inserted text stays selected with the cursor at its end, and the edit is one undo step that leaves the document dirty. The chooser starts in the document's folder. Failure modes: the action does nothing in Diff Mode, is disabled for read-only documents (a toast explains if it is reached anyway), and refuses with an error dialog a path that is not a regular file, a file above 16 MiB, an unreadable file and a file that is not valid UTF-8; nothing is inserted in any of these cases. A file above the 1 MiB soft cap asks for confirmation first. An empty file inserts nothing and shows a toast. A leading UTF-8 byte-order mark is dropped. If the document has uniform LF or CRLF line endings, the inserted text is converted to that style so the insertion cannot make the document mixed; a document with no line breaks yet or with mixed endings keeps the file's endings as they are. Tabs are converted to spaces by the same `insert-text` filter as pasted text, with its toast. The logic is in `core::insert`; the window owns the chooser, the confirmation and the buffer edit.
- **Edit Indentation** (right-click context menu) sits at the bottom below a separator. Its submenu has **Increase (skip empty lines)** (`win.indent-increase-skip-empty`, **Ctrl+Alt+]**), **Decrease (allow flattening)** (`win.indent-decrease-allow-flattening`, **Ctrl+Alt+[**), **Increase (include empty lines)** (`win.indent-increase-include-empty`, **Ctrl+]**) and **Decrease (no flattening)** (`win.indent-decrease-no-flattening`, **Ctrl+[**), followed by a section with **Double** (`win.indent-double`, **Ctrl+Shift+]**) and **Halve** (`win.indent-halve`, **Ctrl+Shift+[**). The operations target the lines the selection touches (as in the status bar's selection line count), or every line when nothing is selected, and change only leading ASCII spaces. Increase (include empty lines) adds one space to every target line. Increase (skip empty lines) filters out only lines whose `textlines::content` is truly empty; whitespace-only lines still count. Decrease (allow flattening) removes one space from each target line that has one and leaves unindented lines alone. Decrease (no flattening) requires every participating line to have at least one leading space; otherwise it returns an empty change list and shows no toast. It ignores the empty line after a terminating line break, so a normal newline-terminated file is not automatically blocked; other empty lines still participate. Double and Halve scale the existing indentation and keep their all-or-nothing errors: Double aborts with the toast “No indentation to double” if every target line has zero indentation; Halve aborts with “No indentation to halve” in that case, and also aborts if any target line has an odd number of leading spaces, with the toast “Cannot halve indentation: line {line} has an odd number of leading spaces” naming the first such line (1-based). The Increase and Decrease variants show no success or failure toast. An aborted Double or Halve changes nothing, and a successful operation shows no toast. Each operation is one undo step and keeps line breaks untouched. All six actions are disabled for read-only documents and do nothing while Diff Mode is showing. Double and Halve also register the shifted brace keyvals (`braceright`/`braceleft`) so the physical Ctrl+Shift+] and Ctrl+Shift+[ combinations work on platforms that report the shifted symbol. The planning logic is `core::indent::plan`; the window applies the per-line edits. The menu uses ordinary `Gio.Menu` items, so activation closes it.

- **Trim Trailing Whitespace** (right-click context menu, `win.trim-trailing-whitespace`) removes trailing ASCII spaces and tabs from the lines the selection touches, or from every line when nothing is selected. Whitespace-only lines become empty. It is one undo step and shows a success toast with the number of characters removed, using singular/plural and thousands separators (for example “5 trailing whitespace characters were removed”). The context-menu item is greyed out when the effective target has no trailing whitespace; invoking the action directly in that state reports “No trailing whitespace to remove”. The action is disabled for read-only documents and does nothing in Diff Mode. `core::whitespace::trim_plan` produces the per-line deletions, and `has_trailing_in` drives the sensitivity check when the context menu opens.
- **Status bar:** a bar under the editing area shows `bytes: <n>  chars: <n>  lines: <n> | Ln: <line>  Col: <col>  Pos: <pos>` on the left, and the line-ending style, `UTF-8` and the mode on the right. Every numeric field uses comma thousands separators (`bytes: 12,507`). `bytes` is the UTF-8 byte size of the current buffer text (unsaved edits included) and `chars` is its character count (Unicode scalar values). Both come from `core::textstats::text_stats`. The editor caches the string returned by GTK along with its whole-text measurement, so the status bar can refresh without making a second full-text copy into a Rust `String`. Cursor and selection moves reuse that measurement until the buffer changes.

  `Ln`, `Col` and `Pos` are 1-based: `Col` counts characters and `Pos` is the byte offset plus one. While a selection exists, `Sel: <bytes> bytes, <lines> lines` replaces the `Pos` field; `Ln` and `Col` still describe the cursor, `<bytes>` is the UTF-8 size of the selected text, and `<lines>` counts the lines the selection touches (a selection ending exactly at the start of a line does not count that line). The line-ending field reads `Unix (LF)`, `Windows (CRLF)` or `Mixed`; a text with no line breaks reads `Unix (LF)`. Lone CR and U+2029 breaks count as mixed, matching the line model. The mode field reads `INS`, or `OVR` while overwrite mode is on (toggled by the `Insert` key), or `RO` when the document is read-only (opened read-only under the no-tab policy, or locked from the status bar). The numbers are computed in `core::textstats`.

  The editor bar has a `●` immediately left of the line-ending field. It is green (`.trailing-clean`) with tooltip `No trailing whitespace` when clean, and yellow (`.trailing-dirty`) with tooltip `Find trailing whitespace` when any line ends in ASCII spaces or tabs. Only the yellow dot takes a pointer cursor and activates `win.find-next-trailing-whitespace`, which selects the next run, scrolls it onscreen, focuses the editor and wraps at the end; the action is enabled only while the dot is yellow and remains available for read-only documents. It does nothing in Diff Mode, and Diff Mode pane bars do not have the dot. The dot is updated from the `has_trailing_whitespace` field of the cached whole-text measurement by `window/status.rs`.

  **Last edit:** after the cursor field the editor bar shows the time since the most recent in-memory edit (any change to the buffer made by the user, including paste, Replace, EOL Conversion, indentation editing, Insert and undo), for example `31 seconds ago` or `5 minutes ago`, without a label prefix. The elapsed time shows a single unit, floored: seconds below a minute, minutes below an hour, hours beyond (`core::elapsed`). The field is hidden until the first edit and is cleared whenever a document is opened or reloaded, since loading is not an edit. Saving does not reset it. A one-shot timer keeps the text current and is rescheduled each time for the moment the text can next change (`core::elapsed::next_refresh_secs`): every second during the first minute, then at each minute boundary, then at each hour boundary. After the first minute, an idle window wakes up at most once a minute. A new edit restarts the timer, and clearing the edit cancels it. The timer holds the window weakly and does nothing once the window is freed. Diff Mode pane bars do not have this field; their headers show an absolute last-edit or last-save timestamp instead. The status bar's non-widget state (cached buffer measurement, idle-refresh flag, last-edit instant, wall-clock edit time and timer) lives in `StatusState` in `window/status.rs`.
  During the first second after an edit the field reads `just now`; at one second it becomes `1 second ago`. Refresh timing and the later minute/hour boundaries are unchanged.
  The timer also pauses while the window is inactive: losing focus cancels it, and regaining focus refreshes the text once and reschedules it (`connect_status_activity`), so idle background windows cause no periodic wakeups.

  Refreshes are triggered by text changes, cursor moves, selection changes and mode toggles, but several of these signals fire for one keystroke, so they are coalesced into a single refresh on idle. The buffer text and its whole-text stats are cached and re-measured only after the buffer changes, so cursor and selection moves never re-copy the buffer. Clicking the line-ending field opens the EOL Conversion popover with **Windows (CRLF)** and **Unix (LF)** choices, built by `build_eol_menu`. Clicking the mode field (`INS`, `OVR` or `RO`) opens a popover with one checkable **Read Only** item (`build_mode_menu`, the stateful action `win.read-only`, disabled in Diff Mode). Locking is immediate. Unlocking a document that still contains tab characters follows the no-tab policy: the Convert Tabs prompt appears, **Yes** converts the tabs (one undo step, document dirty) and unlocks, and **No (Read Only)** or Cancel keeps it locked. `set_read_only` keeps the action's check mark in sync with the real state.
- **No tab characters:** notediff keeps tabs out of documents.
  - Opening a file that contains a tab character shows a **Convert Tabs** dialog: “The target file contains tab characters. Convert them to spaces?” with **Cancel**, **Yes** (red/destructive), and **No (Read Only)** (blue/suggested), in that order. **No (Read Only)** is the default for Enter; Esc cancels. Open and reload share this dialog.
  - **Yes** converts each tab to one space. The document opens dirty, because its text now differs from the file on disk.
  - **No (Read Only)** opens the file with tabs intact and the editor non-editable, with `RO` in the status bar.
  - **Cancel** aborts the open. A window created only for that file (command-line launch) closes.
  - The **Tab** key never inserts a tab. With no selection it inserts one space (in overwrite mode it overwrites the next character on the line with a space instead, and inserts at the end of a line). With a non-empty selection it indents every touched line by one space (blank lines are skipped). **Shift+Tab** removes one leading space from each touched line, or from the cursor's line when nothing is selected. A line operation is one undo step.
  - **Pasted or dropped text:** tabs in any text inserted into an editable buffer are converted to one space each as they arrive (a handler on the buffer's `insert-text` signal), and a toast says so. Programmatic loads (open and reload) bypass this filter because they follow the Convert Tabs policy instead.
  - **Reload from Disk** (the external-change dialog) applies the same Convert Tabs prompt when the file on disk contains tabs: **Yes** converts and leaves the document dirty, **No (Read Only)** reloads with tabs intact and locks the editor, and **Cancel** aborts the reload, leaving the editor text and the document untouched (the window remembers the disk modification time it declined, and the external-change prompt returns only once that time changes). The disk text is inspected before the document is modified. As a defence against a race, `show_document_text` re-checks the text: if a file that was peeked as tab-free gained tabs before it was read, it is loaded read-only (with a toast) rather than into an editable buffer.
  - `core::tabs` holds the detection and conversion logic, and the window owns the prompts, the insert filter and key handling. Read-only is a per-window state that is reset whenever a document is loaded or reloaded.
- **About notediff** (menu) opens a dialog that shows everything at once, with no tabs or extra pages: the app name, the version (a blue button that copies it to the clipboard when clicked), a short description, the release date (November 18, 2026), a copyright line (`© 2026 Robert Hewitt (AverniteDF)`), and the no-warranty notice linking to the MIT License. Name, version, author and description are read from `Cargo.toml` at compile time, so the version (currently 1.1.0) has a single source of truth.
- Per open file, two in-memory buffers matter: the **Live Draft (`D`)**, and the **Baseline (`S`)**, loaded from the snapshot store when Diff Mode is entered.
- Normal saves write `D` to the live file only.
- **Unsaved-changes tint:** besides the larger `●` and two spaces before the file name in the title, a dirty document gives the window the `notediff-dirty` CSS class, which gently tints only the main window's header bar with the scheme's `notediff:accent` colour (a 35% blend with the normal header-bar background, resolved by `ui::theme_palette`; the dark default is `#e0b36b`, the light default `#b36605`, and an explicit style overrides either). A dedicated class on the main header bar keeps dialogs such as Manage App untinted. Status bars keep their normal appearance. `update_title` toggles the class, so it follows every change of the dirty flag. A read-only document appends ` (Read-Only)` after the file name, and `update_title` is refreshed whenever read-only state changes. The header title is a custom ellipsized label; `update_title` sets its full-path tooltip, or clears it for an untitled document. The tooltip is suppressed while the right-click copy menu is visible and restored when it closes. A right-click menu on the label offers `Copy file name` and `Copy full path` through the `win.copy-file-name` and `win.copy-full-path` actions, with `Copied file name` / `Copied full path` toasts. Both actions are disabled for untitled documents.
- The app has switchable themes (section 5.7). The default is the dark, low-glare `notediff Dark` theme with soft, low-contrast colours. Editor and diff content use a larger monospace size than the rest of the UI; the line-number gutters scale with it.
- Files are opened individually. There is no required “project folder”. An optional file-tree sidebar can be added later.

### 5.2 Diff Mode (Review Changes)

Entered from the **Review Changes (F5)** header button or `F5`. There is no main-menu entry. The header button reads **Review Changes (F5)** only once the open file has a baseline; before that it is **Create Baseline**, or **Save As** while the document is untitled (section 5.5), and `F5` only shows a short notice.

- **Left pane:** the live document `D`, **read-only**, with changed regions highlighted. Its header shows the canonical live path, middle-ellipsized with the full path as a tooltip.
- **Right pane:** the baseline `S`, read-only to the user, mutated in memory only by the accept and undo commands. Its header reads `Baseline`. Both headers show a right-aligned local timestamp in `YYYY-MM-DD HH:MM` form. The live time is the last in-memory edit, or the file mtime before the first edit; the baseline time is the snapshot file's mtime, so in-memory accepts do not change it. The live tooltip reads **Last edit** after an edit or **Last saved** before one; the baseline tooltip reads **Last saved**. The Confirm button shows the uncommitted accepted count, for example `Confirm (1 change)` or `Confirm (3 changes)`. Whole-hunk and individual inline accepts each add one; Accept All adds the number of whole hunks accepted and is one undo step. Undo restores the previous count. The count is independent of remaining hunk regrouping.
- **Pane status bars:** each pane has a status bar below it showing `bytes`, `chars`, `lines` (with thousands separators), the line-ending style and `UTF-8` for that pane's text. The panes are read-only with hidden cursors, so the cursor and insert-mode fields are omitted. The bars are refreshed on every render (entering Diff Mode, accept, accept all, undo), so the baseline bar reflects the in-memory `S`.
- **Highlighting:** line-level hunks as background tags, plus word-level highlights within changed lines (from `similar`'s inline diff) so single-word edits inside long paragraphs are visible. Adjacent changed words separated only by whitespace share one continuous highlight; unchanged words and punctuation separate highlights, matching the inline review units. Normal hunks and words use two fixed amber shades; focused regions use two fixed red shades. Dark themes use white foregrounds; light themes use black foregrounds and lighter backgrounds. Dedicated XML styles can override each exact opaque pair; no editor-background blending is used. Blank lines inside a hunk show a display-only pilcrow (`¶`) with the word-level background (strong amber, or strong red when the hunk is focused) and a faded foreground, so an empty change stays visible without looking like real text. The marker is stripped from copied and accepted text. When one side gains or loses a final newline, the display-only line after that newline belongs to the last hunk and is marked the same way. A focused pure insertion or deletion shows a 3px strong-red boundary bar on the pane whose side is empty, at the exact insertion/deletion point, so that pane still shows where the change belongs. The bar scrolls with its text on both axes. In the full diff, line numbers on the focused hunk's rows use the theme's stronger `current-line-number` style (bold when the theme specifies it), including the single boundary row when that side is empty; all other rows use the normal `line-numbers` style. Inspection panes continue to hide line numbers.
- **Re-diff:** recomputed after every accept or undo, since only `S` changes. The line diff and inline refinement share a one-second deadline; a timed-out diff is still valid and the UI remains usable. Accept-all builds its result in one pass.
- **Initial state:** every time Diff Mode is entered, vertical and horizontal scrolling in both panes is reset to zero and no hunk is focused, so the user starts at the top of the file. The first `Up`, `Down`, Previous or Next input focuses the first hunk (in either direction), scrolls both panes to their own anchors and resets horizontal scrolling. Until a hunk is focused, **Inspect** and **Accept** are disabled and `Right` does nothing. **Accept All** works from the full diff.
- **No word wrap in the full diff:** both panes use `WrapMode::None`, so a line is one display row and the panes stay aligned vertically; long lines scroll horizontally.
- **Equal widths:** the panes sit in a homogeneous `GtkBox`, so they are the same width (within one pixel) at any window size. The divider is a CSS border on the right pane, which takes no part in the allocation. Pane titles ellipsize (the full path is in a tooltip) so a long path cannot widen one pane.
- **Scrolling:** each pane scrolls independently in both axes. Mouse wheel, scrollbar, touchpad and Page Up/Page Down affect only the pane being scrolled. Moving focus to a hunk with Up/Down or the toolbar buttons scrolls each pane to its own anchor and resets both horizontal positions to zero; focus changes from Accept/Undo do the same. The full diff leaves lines unwrapped. Page Up and Page Down work normally (on the Chromebook keyboard these are Alt+Up and Alt+Down at the system level).
  Accept and Undo do not replace unchanged pane text. Changed text is updated with the smallest contiguous replacement (common prefix/suffix retained, UTF-8-safe character offsets), preserving layout and marks outside the edited range instead of clearing the baseline and causing a visible repaint. During buffer updates and hunk placement, each pane validates its anchor and settles its layout independently across frames. A generation counter makes the latest scroll request win (including rapid Accept → Undo); unmapping cancels pending placement. This prevents deferred long-document layout from pulling a pane away from the restored hunk.
- **Scroll alignment:** the panes have different line counts around changed hunks. Each pane scrolls to the focused hunk’s own line anchor; the two panes are not linked and may use different adjustment values. Horizontal scrolling is reset to zero on hunk navigation.
- **Entering does not save `D`.** Diff Mode compares the baseline with the current editor text, so unsaved edits can be reviewed and navigated immediately. Accepting and undoing stay in memory and need no save. **Confirm** and **Create Baseline** need a saved document: a dirty document gets a **Cancel / Save** prompt, and choosing Save saves first and then commits the baseline. Cancelling or dismissing the prompt changes nothing and keeps the current Diff Mode view open. Closing the window confirms before discarding accepted in-memory hunks and never writes the baseline; a dirty live document still gets its save prompt first.
- **Untitled documents:** until the document has a path, the header button reads **Save As** on a blue (suggested-action) background and opens the Save As dialog. `F5` does nothing, because a baseline must be keyed by path. Once saved, the button becomes **Create Baseline**.
- **No changes:** if `S` already equals the current `D` when the user opens Review Changes, the header button briefly reads **No Changes** and Diff Mode is not entered.
- **In sync:** when the diff is empty, both panes stay visible with identical content. Previous, Next, Inspect, Accept and Accept All are disabled; Undo is enabled whenever the undo stack has an entry. Green Confirm indicates completion. There is no information row or separate “No differences” status page.
- **Close/Back/Confirm button:** the right-aligned toolbar button reads **Close** in the full diff or **Back** in inspection while no uncommitted changes have been accepted. With uncommitted accepts it reads **Confirm** in either view; **Confirm** turns green when no differences remain. Confirm writes the accepted baseline to disk. A partial Confirm stays in the current view, resets the accepted count and clears accept-Undo history, preserving focus and scroll position; in inspection it becomes Back. Green Confirm writes and returns to Standard Editor Mode. Back returns to the full diff without writing and becomes Close; Close returns to the editor without writing. Closing the window asks before discarding only uncommitted accepts, and still offers to save a dirty live document first.
- **Dialogs own the keyboard:** while a save prompt, error dialog or Manage App… → Baseline Snapshots is open, Diff Mode ignores its navigation and accept keys, so dialog keyboard input cannot also trigger a hunk action.
- **File actions while reviewing:** New File, Open File, Save As and Rename or Move are disabled while Diff Mode is showing. The disabled New File and Open File header buttons also drop their shortcut tooltips. New Window remains available, so another file can be opened without disturbing the review. Finishing or closing the review restores the other file actions and tooltips.

#### Hunk inspection

Inspection uses `notediff:focused-hunk` (white on dark red in dark themes;
black on pale red in light themes) for
unselected inline differences, with no added bold or underline. The selected
change retains `notediff:focused-word` (the stronger red pair); zero-width
boundaries use a strong-red overlay caret at the exact insertion/deletion point.
These tags cover only difference spans, not
whole hunks. Full Diff Mode retains amber inline backgrounds. Theme switches
update both inspection foreground/background pairs.

- **Entry and exit.** With a focused hunk, **Inspect** (left of **Accept**) or `Enter` switches to inspection within the current Diff Mode session. With no uncommitted accepts the right-aligned Close/Confirm control becomes **Back**, with tooltip `Return to full view (Enter)`; there is no separate Back button beside Accept. Back returns to the full diff without changing the selection or writing to disk. Pending accepts take priority: the control is Confirm until committed or undone. `Esc` and `Enter` always return to the full diff from inspection, preserving pending accepts. The Accept label is unchanged between views, while its tooltip distinguishes a selected hunk from a selected change. There is no hunk-position counter, keyboard-help row or change-description row. Panes sit immediately below the toolbar. Other tooltips remain short. Close has no tooltip; Confirm says `Update baseline` or, when green, `Sync baseline`. A new session always starts in the full diff.
- **Presentation.** A separate persistent pair of read-only inspection panes shows the selected change's containing hunk. Exact LF, CRLF and final-line boundaries are retained. Inspection uses `WrapMode::WordChar`, hides excerpt-relative line numbers and scrolls independently. No whole-hunk background is applied: unchanged context uses the normal editor background, other differences use the focused-hunk review palette, and the selected change uses the stronger focused-word palette. Text selections intersect the review range with those word-level spans so adjacent whitespace is not selected; block selections cover their full range. Both are rebased to excerpt character offsets and highlighted with the focused palette without an underline. Empty ranges use a 3px strong-red overlay caret at the exact boundary; no adjacent character is tagged or styled as part of the edit. The caret scrolls with the text and is repositioned after wrapping or resizing. Its overlay stays mapped and paints only while active, so a caret repaint never depends on widget map or allocation timing. Full Diff Mode retains its existing whole-hunk highlighting, and marks the empty side of a focused pure insertion or deletion with the same 3px strong-red boundary bar; unfocused hunks get no full-pane boundary marker. Pane headers keep the live path or `Baseline` label and their timestamps, with no empty-side annotations. Status bars describe the excerpts. There is no change-description label. Each pane scrolls to the selected character offset, not simply to the top. Focus restoration targets the active pane pair.
- **Review actions.** In inspection, Previous/Next and Up/Down traverse a globally ordered list of pending individual changes, including changes within the same hunk, without wrapping. Accept/Right applies only the selected unit. Live-text byte offsets anchor advancement after re-diffing, and the pre-accept hunk's live byte span defines the inspected region, so a re-diff split still counts as one region. A successor inside that span is followed; otherwise, while pending changes remain in the span, the nearest remaining change above the accepted one is selected. Inspection advances to the next pending hunk only when the region is drained; with no next hunk it falls back to the last remaining change. Accepting the final change returns to the full, in-sync view. Undo snapshots restore both hunk and inline selection while inspection is active; after automatic exit, Undo restores a full-diff selection. Toggling an unchanged inspection remembers the selected unit. Full Diff Mode retains whole-hunk accepts and **Accept All**.
- **Commit and return.** Confirm retains its save behavior. A successful partial Confirm retains inspection, selection and scroll positions, clears accept history and changes the right-aligned button to Back. Back returns to the full diff; Close is available there. Cancelling the save prompt or a write failure leaves inspection and pending accepts intact.
- **Inline change model.** `core::inline` represents paired baseline/live byte ranges, not GTK line or visual-row coordinates. Equally sized line blocks are paired positionally using the existing diff policy. Consecutive word-token Delete/Insert runs form one atomic replacement; equal non-whitespace tokens separate review units, while equal whitespace bridges adjacent changes into one phrase-level unit. Bridged whitespace extends both ranges when a change continues, and identical leading/trailing whitespace is trimmed from review units, so applying one never duplicates whitespace. Line terminators are separate units and never normalized. A wholly inserted/deleted hunk is one atomic block: the complete non-empty excerpt uses the stronger focused-red background, Right accepts it in one undoable step, and Up/Down moves to another change rather than another line. Unequal non-empty multiline replacements use an atomic block fallback rather than guessing a pairing. Applying a change validates UTF-8 range boundaries and replaces only its baseline range. The session regenerates changes after every accept/undo, retaining exact undo selection and advancing by immutable live coordinates. Deterministic randomized tests cover arbitrary acceptance order, regrouping, Unicode, whitespace, mixed endings and convergence to byte-identical live text.
- **Persistent full diff.** Each pane has a transition-free GTK stack holding full-document and inspection views with distinct buffers and adjustments. Inspection never replaces or rewraps the full-document buffers. A session content revision changes only on Accept/Undo; the full diff updates its baseline incrementally and caches whole-document statistics at that revision. A plain toggle does not fetch or edit full buffer text, recompute whole-document statistics, retag the full diff, or queue scroll placement. Full-diff viewport positions are retained naturally, without opacity masking or viewport snapshots. Inspection navigation and text changes position the retained full views at the recomputed hunk, synchronously validating their anchors before they are shown; generation-guarded placement also handles deferred GTK layout. Full and inspection placement have independent generations. Unmapping cancels both. The long-document smoke scenario checks retained buffer identities, zero buffer edits and zero scroll requests for plain toggles, exact vertical/horizontal position retention, return latency, and hunk visibility on presented frames through navigation, Accept/Undo and rapid transitions.

### 5.3 Navigation and Commit Keys

Neither pane is editable in Diff Mode, so arrow keys are free to drive hunk actions:

| Key | Action |
| --- | --- |
| `Up` / `Down` | Previous/next hunk in full diff; previous/next individual change in inspection. No wrap. With no full-diff selection, either key focuses the first hunk |
| `Right` | Accept the focused whole hunk in full diff, or only the selected individual change in inspection; update in-memory `S`, re-diff and advance |
| `Left` | Undo the last accept in memory (restores the previous `S`) |
| `Enter` (including keypad Enter) | Inspect the focused hunk or return to the full diff |
| `Esc` | Return to the full diff from inspection. In the full diff, leave Diff Mode, confirming first when changes have been accepted |

Accept All is available from the full diff toolbar. Space activates focused toolbar buttons.

Implementation note: read-only `GtkTextView` widgets would normally consume the arrow keys to move the text cursor. The window therefore installs a key controller in the capture phase that handles these keys itself while Diff Mode is shown, and the diff panes hide their cursors.

Diff Mode is entered with `F5` or the **Review Changes (F5)** header button. The Diff Mode keys are handled in one `match` in `window/diff_actions.rs`, and the menu accelerators are listed together in `install_accels` in `window/menus.rs`. The right-aligned toolbar button is labelled **Close**, **Back** or **Confirm** depending on the view and uncommitted progress (section 5.2).

Accepts and undos only change the in-memory `S`; the baseline on disk is written once per Confirm. **Confirm** is blocked behind the save prompt when `D` is dirty, so the snapshot always corresponds to a saved live document. Closing the window confirms before discarding uncommitted accepts without writing the baseline; a dirty `D` gets its save prompt first. If the snapshot write fails at **Confirm**, the error is reported and Diff Mode stays open with its accepted state intact, so the user can retry or undo. Because accept-all is one undo step, it needs no confirmation dialog. The undo stack is in memory and is cleared after each successful partial Confirm. **Left** undoes one accept. In the full diff, **Esc** leaves Diff Mode: with accepted changes it first shows `Discard accepted changes?` with Cancel and Discard and Exit Review; the same confirmation is used before closing a window or quitting. The live document and saved baseline are not changed.

### 5.4 Hunk Application Semantics

This is the core of correctness, so it is specified precisely:

- A hunk maps a line range in `S` to a line range in `D`. Accepting replaces the `S` range with the `D` lines, preserving each line’s original line ending.
- The final-newline case is handled explicitly. A file that gains or loses a trailing newline produces a hunk on the last line, and accepting it must reproduce the exact bytes of `D`.
- Blank lines are interchangeable diff anchors. Consecutive deletion-only and insertion-only hunks separated only by unchanged blank lines are coalesced into one hunk when both sides contain non-blank changed content, so a replacement split around a blank line is accepted as one change. Paragraph replacements and blank-only insert or delete runs remain separate.
- Accepting all hunks must leave `S` byte-identical to `D`. A deterministic property test covers this: for random pairs of texts, accepting every hunk in any order, re-diffing between each, ends with `S == D`.
- The undo stack holds full prior copies of `S` and is bounded to 100 entries or 64 MiB of retained baseline bytes, whichever comes first. The newest snapshot is always kept.

### 5.5 Create Baseline (No Snapshot)

There is no separate commit view. The header button reflects the state of the open file:

- **Untitled document:** the button reads **Save As** on a blue (suggested-action) background and opens the Save As dialog. There is no tooltip. Once saved, the button becomes **Create Baseline**.
- **File open, no baseline yet:** the button reads **Create Baseline**. Clicking it writes `D` to the snapshot store and nothing else: the user stays in the editing view and Diff Mode is not entered. The button immediately becomes **Review Changes (F5)**, disabled until the text differs from the new baseline. The document must be saved first; a dirty document gets the same Cancel / Save prompt as Confirm.
- **File open, baseline exists:** **Review Changes (F5)**, enabled while the live text differs from the baseline and disabled once they match or while Diff Mode is showing. Its `Compare with baseline` tooltip is omitted while Diff Mode is showing. `F5` still flashes **No Changes** when there is nothing to review. The window caches the baseline text and compares the measured buffer against it on the coalesced idle pass; it never recomputes the full diff just to choose the button state.

The button state is refreshed when a file is opened or saved, after a baseline is created, after the file is renamed, when the window regains focus, when Manage App… → Baseline Snapshots closes (in case a baseline was deleted or linked), and when an edit settles and its comparison with the baseline changes.

### 5.6 Baseline Snapshots

**Manage App.** The main menu has one **Manage App…** entry (no submenu), which opens a single dialog (`ui::app_dialog`) with a tab for each page: **Baseline Snapshots** (`ui::app_dialog::snapshots_tab`, described here) and **Appearance** (section 5.7), which combines theme selection with font family and size controls. Both tabs are built on `ui::app_dialog::cleanup_dialog` and share the dialog's toast overlay. A `GtkStackSwitcher` provides text-only tabs without placeholder icons. When the dialog closes, the main window refreshes its header button.

Orphan handling is an on-demand dialog (menu: **Manage App…**, **Baseline Snapshots** tab), not a launch-time step. Since breaking the association is the user’s responsibility, this is a convenience for tidying up, not a safety mechanism.

- Walks the snapshot store and lists snapshots whose live file no longer exists at the mirrored path, with the path and last-modified date.
- **Skips snapshots whose live path is on an absent volume mount** (for example an unshared `/mnt/chromeos/...` location) and lists them separately as “location unavailable”, not as orphans. A missing folder below an existing mount point is an orphan, not an unavailable location.
- Each orphan has a checkbox. Actions are **Delete selected** and **Close**.
- **Linking.** The dialog is told which document the window has open (`LinkTarget`: canonical path and current editor text). A banner at the top says whether linking is available: not for an untitled document (no path to key a baseline on), not for a document that already has a baseline (linking never replaces one), and otherwise yes. Link and Copy act immediately on a button click, with success toasts and error handling but no confirmation dialog. These buttons have no tooltips. Deletion still requires confirmation: “Only the baselines will be removed. Live documents remain untouched. This cannot be undone.”
- **Link (move).** When linking is available, each orphan row has a **Link** button. The orphan's baseline is written under the current document's mirrored path and the old snapshot is then deleted, because the old live file is gone. Live files are not touched, and no save prompt is involved: unlike Create Baseline, linking does not snapshot the draft, and Diff Mode already compares the baseline with the unsaved editor text.
- **Copy.** A collapsed **Copy a baseline from another file** section lists snapshots whose live file still exists, with a path filter. **Copy** leaves the original in place, so both files end up with an independent baseline. This covers the common "Save As, then compare against the old file's baseline" case, which orphans nothing (Save As also offers this directly, see section 5.1). Snapshots on unavailable volume mounts cannot be linked.
- **Ranking.** Both lists put snapshots with the same file name first, then the most similar to the current editor text (line-based ratio from `similar`; not measured for texts or snapshots above the 1 MiB cap, or for an empty document), then the most recently modified. Rows show "Same file name" and "N% similar" badges. Ranking only orders suggestions.
- The store logic is `SnapshotStore::link` with `LinkMode::{Move, Copy}` (refuses a source outside the store, a self-link and an existing target baseline); ranking is `core::relink::rank`.
- Deletion is never silent and never automatic.
- The dialog explains that renamed or moved files leave their old snapshot behind, and that deleting an orphan only discards a baseline.
- When the dialog closes, the main window refreshes its header button so it reflects the current baseline state.

### 5.7 Appearance

The **Appearance** tab of **Manage App…** (`ui::app_dialog::appearance_tab`) picks the application theme.

- **Hidden shortcuts.** Alt+T selects the next catalog entry; Alt+Shift+T selects the previous entry. Both wrap, suppress autorepeat and reset their held-key state on activation loss. The name is shown in a toast, the choice is remembered and open pickers follow global changes. Shortcuts remain absent from menus and keyboard hints.
- **Picker.** One plain-text `AdwActionRow` per successfully loaded theme, with a grouped check button, name, description and a two-part sample: the gutter background with a normal line number `1`, then one non-selected sample line of text. Clicking applies globally without an Apply button. Font controls retain their separate **Apply Font** button. Load diagnostics are selectable text on the Appearance page and also go to standard error. The page explains the restart policy; there is no installation/reload control.
- **Owned catalog.** `core::themes::Theme` owns only ID, name, description, dark/light mode and scheme ID. `ui::theme_catalog::LoadedTheme` owns that metadata, the actual optional fallback/resolved scheme, its manager and one resolved palette. The startup catalog and current selection hold `Rc<LoadedTheme>`; callbacks capture owned clones rather than static references. Dark and Light remain built-in, in that order. The opt-in examples under `examples/themes/` are Cola & Cream, Forest Dusk, Grape Bubblegum and Slate Haze; none is embedded or installed automatically.
- **User format and ordering.** Read immediate real directories of `$XDG_DATA_HOME/notediff/themes`, sorted case-sensitively by OS filename ordering; ignore symlink directories and loose files. Each has a UTF-8 `theme.conf` and `scheme.xml`. The descriptor has exactly four required keys, each once: `id`, `name`, `description`, `mode`; blank lines and whole-line `#` comments are allowed, with unquoted trimmed values, no empty/control-containing values or unknown keys. Mode is `dark`/`light`. IDs have 1–64 ASCII bytes, start with a lowercase letter and otherwise contain lowercase letters, digits or hyphens. `dark`, `light` and the `notediff-` prefix are reserved. The required XML scheme ID is derived as `user-<id>`. First loadable duplicate ID wins; a bad earlier XML does not reserve its ID. User entries follow the two built-ins.
- **Loading and diagnostics.** Each bundle has an isolated `StyleSchemeManager`, prepending its canonical `scheme.xml` file to default GtkSourceView search paths unless the file contains a line-number sentinel. In that case notediff writes a sanitized copy to `$XDG_DATA_HOME/notediff/styles/<scheme-id>.xml` and loads that copy; the bundle's `scheme.xml` remains the source of truth. Parent/use-style resolution stays with GtkSourceView. The resolved scheme filename must match the file that was loaded, preventing accidental selection of another scheme with the same ID. Cross-bundle dependencies are unsupported. Missing roots are normal; other scan/descriptor errors, missing/mismatched/invalid schemes, failed parent resolution and duplicate IDs produce diagnostics and skip that user entry. Built-ins are atomically installed under `$XDG_DATA_HOME/notediff/styles`; failures are diagnosed and try `Adwaita-dark`/`Adwaita`, then report a missing fallback as well. Palettes always resolve from the scheme actually applied, including fallback schemes.
- **Palette.** `ui::theme_palette` resolves effective styles and honours `foreground-set`/`background-set`. Review styles `notediff:hunk`, `notediff:word`, `notediff:focused-hunk` and `notediff:focused-word` use exact foreground/background pairs, including parent/use-style inheritance. Dark standard backgrounds are respectively `#664400`, `#8a5a00`, `#702020` and `#ad3030`, with white foregrounds. Light standard backgrounds are `#fff0c2`, `#ffd477`, `#fad6d6` and `#f39a9a`, with black foregrounds. The built-in schemes include these values as a reference; user schemes may omit the review styles, and missing styles and unset/invalid/translucent fields use the matching mode-standard fallbacks, based on declared mode rather than measured editor colours. Valid explicit XML overrides take precedence in either mode. Unreadable pairs below 4.5:1 revert to their complete mode-standard pair with a diagnostic. There is no blending or opacity stacking. Each diff tag applies its own pair, including inline selected/boundary tags in inspection, overriding the editor text colour inside highlights. Preview colours come from the scheme's `text` and `line-numbers` styles. The gutter uses the normal line-number colour as-is; the sample text uses a readable contrast fallback. If `line-numbers` has no foreground, or its foreground is `auto`/`NN%`, notediff derives it from `current-line-number` at 50%/NN% opacity. These sentinels are stripped from the scheme before GtkSourceView loads it. The derived colour also supplies a gutter CSS override for the editor. An explicit `line-numbers` colour wins unless a sentinel is present; an inherited parent colour counts as defined when there is no sentinel. Invalid percentages fall back to `auto`. The dirty header mixes the dedicated `notediff:accent` style with the libadwaita header at 35%; when that style is absent, a mode-standard accent is used. The dark standard accent is `#e0b36b` and the light standard is `#b36605`; the built-in schemes include them as references. Original editor colours outside app highlights are retained; low base-text contrast is diagnosed, with no guarantee for arbitrary theme styles or all header/system combinations.
- **Applying.** `theme::apply` changes only in-memory selection, libadwaita mode, every live buffer's already-loaded scheme, CSS and DiffPage tags (full and inspection pairs). Buffers are weakly registered with pruning and identity deduplication. Listener invocation releases the registry borrow before callbacks run. Keep the window registry's strong `Rc<AppWindow>` ownership: no shared weak-registry abstraction is warranted by a single real weak GObject consumer. Appearance changes do not alter text, dirty/read-only flags, undo or review sessions.
- **Reload policy.** Build the catalog once at startup before buffers/windows, then retain it, schemes, managers and palettes for the process lifetime. Adding, editing or removing bundles takes effect after restarting the app. No file monitoring, in-app installer or runtime rescan is introduced. Switching themes and applying fonts never rereads XML or preference files.
- **Restore Defaults.** The Appearance page's bottom-left action occupies the same position as Delete Selected on cleanup tabs, but is not destructive. Without confirmation it applies Dark and `Appearance::default()` (JetBrains Mono, monospace; 12 pt), resets the invoking dialog's font fields and saves both preferences. Other dialogs' font drafts remain independent, while their theme pickers follow the global selection. Installed bundles and document state are untouched. Both saves are attempted independently; failures leave defaults applied in memory and produce one warning toast, otherwise a success toast is shown. Tests disable persistence along with other appearance controls.
- **Persistence.** Save `theme = <id>` under `$XDG_DATA_HOME/notediff/theme` on explicit selection. The last nonempty theme assignment is resolved against the loaded catalog. Missing/unreadable state or an unavailable saved ID selects Dark; unreadable state and unavailable IDs are diagnosed. Startup fallback does not rewrite preferences. Write failure still applies the selection and warns by toast. Smoke tests inject isolated theme/built-in directories and disable state-file reads and writes.

## 6. User Workflow

```
[ Launch ] -> open file(s) via File > Open or command line
      |
[ Standard Editor Mode ]  edit and save D freely
      |
      |  F5 or the Review Changes button; entering does not save D. F5 is a no-op for
      |  untitled documents. The header button shows Save As for an untitled document
      |  and Create Baseline when the saved file has no baseline.
      v
[ Diff Mode: Review Changes ]   Left: D (read-only)   |   Right: S (receives accepted hunks)
      |
      +--> Up / Down            navigate hunks
      +--> Right                accept hunk into in-memory S
      +--> Left                 undo last accept in memory
      +--> Enter / Inspect      show only the selected hunk, wrapped
      +--> Esc                  leave inspection; in the full diff, confirm then leave
      +--> Confirm              save D if dirty, write S; stay if hunks remain
      +--> Close window         confirm discard of in-memory accepts (save D first if dirty)
```

To discard a change in the live text instead of accepting it, the user leaves Diff Mode and edits `D` directly. Hunk rejection is not part of Diff Mode.

## 7. Edge Cases and Decisions

- **External modification:** On window focus (including while in Diff Mode), before entering Diff Mode, and before saving to the current path, compare the file’s modification time with the last read. Focus and Diff Mode entry show a **Reload from Disk** / **Keep Current Text** dialog with no Cancel button; `can-close` is false, blocking Esc, outside clicks and close requests. After a real response the choose callback explicitly force-closes the dialog, since `can-close` also blocks the response buttons' automatic close. Keep preserves text and review state and continues the pending action, without acknowledging the disk modification time; the same change can prompt again on a later check. In Diff Mode the prompt warns that reloading returns to the editor and discards unconfirmed review changes, leaving the saved baseline untouched. A failed reload or cancelled Convert Tabs prompt also preserves the review session. Only a successful reload exits Diff Mode.
  Saving shows a separate **Cancel / Overwrite** prompt so Ctrl+S cannot silently replace a change made while the window was focused; cancelling that prompt drops the save and keeps the document dirty. This works on every filesystem. Change notification itself uses modification times; `GFileMonitor` is future work (section 10) and is not relied on for `/mnt/chromeos/` locations.
- **Renamed, moved or deleted live file:** when done outside the app, the baseline is left behind. The renamed file opens with no baseline and shows **Create Baseline**, and Manage App… → Baseline Snapshots can link the orphaned baseline to it (section 5.6). No automatic repair is attempted. **Rename or Move** inside the app carries the baseline along, including to another folder. **Save As** leaves the original file and baseline in place and offers to copy the baseline to the new file.
- **Snapshot manually edited or deleted:** treated like any other baseline state. A deleted snapshot makes the header button show **Create Baseline** again. An edited one is simply a different baseline.
- **Write failures:** if writing the snapshot fails at **Confirm** (permissions, disk full, path conflict), an error is shown and Diff Mode stays open with the accepted hunks, so the user can retry or undo. The baseline on disk is only replaced by the successful single write.
- **Live file unavailable at start (absent mount):** the document is reported as unavailable. Nothing is created or deleted in the snapshot store.
- **Large files:** warn above 1 MiB at open and reload; refuse above 16 MiB at open and reload, and refuse to save a buffer above 16 MiB so the app cannot create a file it would refuse to reopen.
- **Encoding and line endings:** read and write as UTF-8, preserving CRLF versus LF exactly. Files containing a NUL byte are refused. A file with mixed line endings must round-trip unchanged. New line breaks follow the document’s dominant ending.
- **Tab characters:** files containing tabs trigger the Convert Tabs prompt on open and on reload from disk, and tabs in pasted or dropped text are converted to spaces (section 5.1). A converted document is dirty until saved, so Create Baseline and Confirm ask to save first. A read-only document can still enter Diff Mode and create a baseline, because those actions never edit its text.
- **Unsaved drafts:** entering Diff Mode does not save `D`; the draft is compared as-is. Confirm and Create Baseline ask to save first (Cancel leaves both `D` and `S` untouched). Accept, Accept All and Undo operate in memory.
- **Untitled documents:** the header button reads **Save As** and is enabled, while `F5` has no effect until the document has been saved once. An untitled document counts as having unsaved changes only while it holds text, so typing into it and clearing it out again does not trigger a save prompt when closing the window or opening a file.
  A file-backed document is marked dirty immediately after an edit. On idle, `AppWindow::settle_dirty` checks GTK’s buffer character count against the saved Unicode scalar count cached by `Document`. Different counts establish that the document is dirty without fetching or comparing text in the dirty check. Equal counts use `Document::differs_from` on the text cached for the status bar. Exact equality clears the dirty flag, including after undo or manual reversion. The idle step coalesces operations such as Replace All.
- **Identical baseline:** opening Review Changes when `S == D` flashes “No Changes” on the header button for one second and does not enter Diff Mode.
- **Symlink changes:** if a symlink is retargeted, the canonical path changes and so does the baseline. This is the same accepted breakage as a rename.

## 8. Implementation Notes

- **Diff UI:** two `GtkSourceView` widgets in a homogeneous `GtkBox`, each with `GtkTextTag`s for hunk background and word-level highlights from the normal palette, plus stronger focused-hunk variants of both. Retag the buffers after every re-diff. Pane headers show the live canonical path and `Baseline`, with right-aligned local modification timestamps; the Confirm button shows the number of changes accepted since the last Confirm, for example `Confirm (3 changes)`.
- **Theme:** libadwaita follows the catalog entry's mode. Editor, full diff and inspection buffers share the entry's loaded GtkSourceView scheme; `ui::theme_palette` supplies all app highlight/preview colours and the dirty-header tint. `assets/notediff.css` remains embedded with font/class/tint placeholders filled by `theme::stylesheet` and reloaded in the existing provider. Built-in scheme installation and optional fallback are owned by `ui::theme_catalog`; see section 5.7 for user bundles, diagnostics and the restart-only policy.
  The same class uses `core::appearance::Appearance` for a font family list and size (defaults `JetBrains Mono, monospace`, 12 pt). Manage App → Appearance stages font edits until **Apply Font**; applying affects every existing and future content view, including line numbers, without changing document text, dirty/read-only flags, undo history or diff session state. `ui::initialize` loads `$XDG_DATA_HOME/notediff/appearance` once, applies it before installing CSS, and no other theme/CSS operation reads state. `theme::apply_appearance` only updates memory and reloads the same CSS provider; theme changes retain these font settings. App-created smoke-test windows use defaults and disable font persistence together with theme persistence.
  `Appearance` has private fields and a validated constructor. Font families are comma-separated names containing letters, digits, spaces, hyphens or underscores, starting with a letter or underscore; no empty names are allowed, and the list is at most 256 UTF-8 bytes. The settings file stores them unquoted; the generated stylesheet quotes non-generic names so digit-leading tokens are valid CSS. Font size is an integer from 6 to 48 pt. The app-written state uses `font_family = ...` and `font_size_pt = ...` lines; invalid lines are ignored independently and the last valid value of each field wins. Missing/unreadable state means defaults. Apply Font saves with `core::fsutil::atomic_write`; failed persistence leaves the applied settings active and shows a warning toast. Newly opened dialogs show current settings; each dialog's font fields are drafts, and applying them replaces both global font values.
- **Save-then-continue:** actions that run after a save prompt (Create Baseline, Confirm, `OpenPath`, New File, Close Window, Quit) are values of `core::pending::PendingAction`. `OpenPath` carries the selected `PathBuf`; the enum is cloned rather than copied. A save to the current path checks the file’s mtime first and asks before overwriting an external change. `require_saved(action)` runs the action at once for a clean document, or shows the prompt for a dirty one. Baseline actions get Cancel / Save. `OpenPath` and New File get Open New Window / Discard Changes / Save, with no Cancel response button; the dialog’s close response still aborts. Closing the window and quitting get Cancel / Discard Changes / Save. Every `Save changes?` prompt has the body `The document has unsaved changes.` For an untitled document the save action reads **Save As**, because it must open the file chooser. `save_then(Some(action))` stores the continuation and `run_pending(action)` executes it. `check_external(ExternalCheck)` takes `ExternalCheck::{Focus, EnterDiff}` (what follows once the document is up to date), and `open_path_after` takes `AfterOpen::{Stay, CloseWindowOnCancel}` (what happens when the Convert Tabs prompt of an open is cancelled). All three enums live in `core::pending`.
- **Window ownership:** A thread-local registry in `window.rs` holds one strong `Rc<AppWindow>` per open window. The application's `window-removed` signal releases that entry when GTK closes the window. This lets the registry release its own reference to the GTK widget during close. The registry also enforces one window per canonical document path: a lookup checks each window's loaded path and its `pending_open` reservation, then raises the owner instead of creating a duplicate. Window signal handlers, actions, controllers, timers and dialog `on_closed` callbacks capture a `Weak<AppWindow>` and upgrade it as needed. One-shot dialog callbacks may hold a strong clone until the dialog is answered. The `weak_handler!` macro supplies the weak capture for unit-returning window signals and for the shared button and action registration helpers. Callbacks with specific return values supply their own fallback. `AppWindow::with_store` lets the UI smoke test inject a temporary `SnapshotStore` and disables theme/font persistence instead of using `$XDG_DATA_HOME`.
- **GTK smoke test:** Theme fixtures use isolated directories, test inherited schemes and missing/invalid/duplicate bundles, and verify saved-ID fallback and schemes/colours in existing and future editors and all four diff buffers. One ignored test runs the editing, file-action and Diff Mode scenarios sequentially on the same GTK thread. It also opens `.rs`, `.md` and untitled documents and asserts that every editor and diff buffer has no language and syntax highlighting disabled. The inspection scenario exercises the key controller, excerpt contents and wrapping, accept and undo, and confirmation. It also covers the external-change overwrite prompt on save, Quit routing a dirty window through its save prompt and closing further windows after the prompt, the Open File save prompt after the chooser (including Open New Window and the absence of a Cancel button), disabled New/Open actions in Diff Mode, and CRLF Enter handling. The Diff Mode scenario closes a realized window, drops the test's strong reference and checks that a weak reference to `AppWindow` can no longer be upgraded.
- **Keyboard handling:** a single `GtkEventControllerKey` on the main window, acting only while Diff Mode is shown, running in the capture phase (section 5.3). It yields to any visible Adwaita dialog and to focused popover menus so their input cannot reach Diff Mode.
- **Window flags:** the plain flags of a window (`dirty`, `read_only`, `allow_close`, `external_dialog_open`, `declined_reload_mtime`, `keep_inserted_line_endings`) live in `DocumentFlags` (`window/flags.rs`). The `loading` flag is set only through `with_programmatic_load(|| ...)`, an RAII guard that clears it even on panic. While it is set the buffer's `changed` handler does not treat the change as a user edit and the no-tab insert filter lets tabs through. `keep_inserted_line_endings` is a separate scoped guard used by Add Text from File after that action has already matched the document's style.
- **Flash state:** the "No Changes" flash of the header button is a `FlashState` (`window/flash.rs`). Each flash has a generation number, and only the timer of the newest flash may end it.
- **Chromebook display:** high-DPI scaling under the container’s Wayland bridge can make fonts, window decorations and the file chooser sensitive to the real display scale.
- **Launching:** `install.sh` installs the release binary and `io.github.AverniteDF.Notediff.desktop` in the user's applications directory, matching the Wayland application ID. The desktop entry passes every selected file through `%F`, and its `Icon` uses the installed themed name `io.github.AverniteDF.Notediff`. It installs a custom overlapping-document icon with blue/amber diff marks in the hicolor theme, both as scalable SVG and 128-pixel PNG, under the same application ID. Icon and desktop caches are refreshed when the relevant utilities are available. `uninstall.sh` reverses the installation without touching snapshots or settings.
- **Transient focus:** `window/focus.rs` restores content focus on idle when the main menu, the Open menu, the title copy menu or the editor context menu is dismissed without choosing an action, and after either title copy action, which only writes the clipboard and shows a toast. The editor context menu is created lazily by `GtkTextView` as a child of the text view; the window keeps an observer on the view's children and hooks that popover's close signal when it first appears. It also restores focus when the last Adwaita dialog closes (including Cancel/Escape on save prompts and closing Manage App… → Baseline Snapshots). It respects an existing/new modal dialog, Find/Replace and the visible Diff Mode pane. Stateless menu action activation is tracked so menu closure does not override a new dialog or file chooser; the two copy actions are excluded from that tracking, and stateful display toggles retain GTK's default activation behavior. This uses only in-window widget focus and does not attempt to activate the application at the compositor level.
- **Dependencies:** no backend and no database. System GTK4, libadwaita and GtkSourceView 5 libraries, plus the Rust crates `gtk4`, `libadwaita`, `sourceview5` and `similar`.

## 9. Summary of Design Choices

- **Live file as source of truth:** the baseline is disposable. Losing it costs a comparison, never content.
- **Central snapshot store:** one folder under XDG data, mirroring absolute paths. Project directories contain no tool artifacts.
- **One baseline per file:** a lightweight save point without history bloat.
- **Read-only live pane, catch-up baseline pane:** one mutating buffer keeps the state machine simple and the keyboard model obvious.
- **Lazy saving:** reviewing compares the live draft as-is; Confirm and Create Baseline ask to save the draft before writing the snapshot.
- **Explicit persistence:** accepts stay in memory until Confirm writes the updated baseline atomically.
- **Focused, readable presentation:** a low-glare dark theme by default (with Light and optional user themes, switchable live from Manage App) and a slightly larger content font keep long editing sessions comfortable without changing the rest of the UI.
- **Plain keys in Diff Mode:** arrows drive review, Enter switches inspection, and Escape backs out one level (inspection to full diff, then Diff Mode to the editor).
- **Confirmed cleanup only:** no snapshot is deleted without explicit user approval.
- **Explicit linking:** a baseline is only linked to a document by an explicit Link or Copy button click and never replaces an existing baseline. Ranking suggests; it never decides.

## 10. Possible Future Work

- Automatic re-linking: proposing a link when a document with no baseline is opened or created, or detecting moves via `GFileMonitor`. (Manual linking exists in Manage App… → Baseline Snapshots.)
- Hunk rejection (revert `S` content back into `D`) from within Diff Mode.
- An optional file-tree sidebar.
- Optional snapshot history, if the single-baseline model proves too limiting.
- A configurable snapshot store location, so it can be synced or backed up independently.
- Per-window zoom (Ctrl+scroll, Ctrl+plus/minus) relative to the persisted application-wide font size, with a reset-to-default action.
